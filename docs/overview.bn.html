০১ / OVERVIEW

প্রকল্প পরিচিতি

ParcelFlow একটি parcel delivery management REST API। কুরিয়ার প্রতিষ্ঠানের দৈনন্দিন কাজগুলো — পার্সেল বুক করা, ডেলিভারি স্টাফ assign করা, পার্সেলের অবস্থা ধাপে ধাপে এগিয়ে নেওয়া, এবং প্রতিটি পরিবর্তনের স্থায়ী রেকর্ড রাখা — এই পুরো প্রক্রিয়াটিকে একটি JSON API হিসেবে তৈরি করা হয়েছে।

তিন ধরনের ব্যবহারকারী একই ডেটা থেকে ভিন্ন ভিন্ন জিনিস চান। একজন customer পার্সেল বুক করেন এবং জানতে চান সেটি এখন কোথায়। একজন delivery staff পার্সেলটি বহন করেন এবং কী ঘটল তা রেকর্ড করেন। একজন admin পুরো কার্যক্রম পরিচালনা করেন, কাজ বণ্টন করেন এবং পরিসংখ্যান দেখেন। API-এর মূল কাজ হলো একই ডেটার উপর এই তিনটি ভিন্ন দৃষ্টিভঙ্গি নিরাপদে সরবরাহ করা।

এই repository-টি সচেতনভাবে backend-only। এখানে কোনো user interface নেই — সেটি আলাদা একটি frontend repository-তে রাখা হয়েছে — email বা SMS পাঠানোর ব্যবস্থা নেই, payment handling নেই, এবং GPS tracking নেই। এটি একটি নির্দিষ্ট linear delivery pipeline-কে মডেল করে এবং সেই pipeline-এর প্রতিটি পদক্ষেপের নির্ভুল হিসাব রাখে।

যে নীতি পুরো প্রকল্পকে আকার দিয়েছে

পার্সেলের ইতিহাস অবশ্যই নির্ভরযোগ্য হতে হবে। এমন যেকোনো কিছু যা একটি ভুল, অনুপস্থিত বা duplicate history row তৈরি করতে পারে — সেটিকে edge case হিসেবে নয়, বরং correctness bug হিসেবে ধরা হয়েছে। নিচের প্রায় প্রতিটি design decision এই একটি নীতি থেকেই এসেছে।

০২ / PROBLEM

কী সমস্যার সমাধান করে

ছোট ও মাঝারি কুরিয়ার প্রতিষ্ঠানে পার্সেলের হিসাব সাধারণত ফোন কল, খাতা আর spreadsheet-এ রাখা হয়। এই পদ্ধতিতে চারটি সমস্যা বারবার ফিরে আসে:

  • দায়বদ্ধতা থাকে না। একটি পার্সেল কখন কার হাতে ছিল, কে সেটির অবস্থা বদলেছে — এর কোনো স্থায়ী প্রমাণ থাকে না। বিরোধ হলে কারও কথার বিপরীতে কারও কথা।
  • যে কেউ যেকোনো কিছু বদলাতে পারে। ভূমিকা অনুযায়ী কাজের সীমা না থাকায় একজন গ্রাহকও নিজের পার্সেলকে "delivered" দেখিয়ে দিতে পারেন।
  • ধাপ এড়িয়ে যাওয়া যায়। পার্সেল pickup না হয়েই "delivered" হয়ে যেতে পারে, কারণ কোনো নিয়ম সেটিকে আটকায় না।
  • গ্রাহক অন্যের তথ্য দেখে ফেলেন। একটি tracking নম্বর অনুমান করে অন্যের পার্সেলের তথ্য বের করে ফেলা যায়।

ParcelFlow এই চারটিকেই কাঠামোগতভাবে বন্ধ করে। প্রতিটি পরিবর্তন একই transaction-এ history-তে লেখা হয়; প্রতিটি endpoint ভূমিকা যাচাই করে; status পরিবর্তন একটি নির্দিষ্ট state machine মেনে চলে; এবং প্রতিটি database query-তে ownership শর্ত হিসেবে যুক্ত থাকে, ফলে নিজের নয় এমন কোনো row কখনো database থেকে বেরই হয় না।

০৩ / FEATURES

প্রধান ফিচারসমূহ

Authentication ও Authorization

JWT
Stateless token authentication

HS256 algorithm এবং issuer দুটোই pin করা, যা alg: none ও algorithm-confusion আক্রমণ বন্ধ করে। Token-এর মেয়াদ configurable।

Fresh identity
প্রতি request-এ user পুনরায় পড়া হয়

Token-এর role claim বিশ্বাস করা হয় না। ফলে কাউকে demote বা delete করলে সেটি পরের request থেকেই কার্যকর হয়, token-এর মেয়াদ শেষ হওয়ার অপেক্ষা করতে হয় না।

RBAC
দুই স্তরের authorization

"এই role কি এই endpoint ডাকতে পারে?" — middleware, উত্তর 403। "এই caller কোন record দেখতে পারে?" — service-এর ভিতরে query scope, উত্তর 404।

Privilege
Register করে admin হওয়া যায় না

দুটি স্তরে আটকানো: Zod strictObject অচেনা role key পেলে 422 দেয়, আর service-এ role সরাসরি CUSTOMER hard-code করা।

Parcel lifecycle

State machine
৫ ধাপের কঠোর linear flow

২৫টি সম্ভাব্য জোড়ার মধ্যে মাত্র ৪টি বৈধ। ধাপ এড়ানো, পিছিয়ে যাওয়া বা একই status আবার সেট করা — সবই 409 দিয়ে প্রত্যাখ্যাত।

Audit trail
Append-only history

প্রতিটি পরিবর্তন — কে, কখন, কোথা থেকে কোথায় — একই transaction-এ লেখা হয়। কোডের কোথাও এই টেবিলে update বা delete করা হয় না।

Concurrency
Optimistic locking

দুজন staff একসাথে একই পার্সেল এগোলে conditional UPDATE-এ একজনের সাথে শূন্য row মেলে, transaction rollback হয় এবং তিনি 409 STATUS_CONFLICT পান।

Tracking
অনুমান-অযোগ্য tracking code

crypto.randomInt দিয়ে তৈরি, বিভ্রান্তিকর অক্ষর (I, L, O, 0, 1) বাদ দেওয়া। Uniqueness database-এর UNIQUE constraint নিশ্চিত করে, collision হলে retry।

Query
Filter · pagination · sort

status, deliveryArea, pickupArea ও আংশিক trackingCode দিয়ে filter; page ও limit দিয়ে pagination; চার রকম sort — সবই index-সমর্থিত।

Assignment
Staff assign ও release

Admin পার্সেল assign করেন; null পাঠালে assignment মুছে যায়। Staff-কে demote করলে তার অসম্পূর্ণ পার্সেলগুলো একই transaction-এ মুক্ত হয়ে যায়।

Admin ও analytics

Statistics
সম্পূর্ণ database-এ গণনা করা পরিসংখ্যান

মোট পার্সেল, status অনুযায়ী ভাগ, unassigned সংখ্যা, delivery rate, গড় ডেলিভারি সময় ও শীর্ষ এলাকা। কোনো row memory-তে এনে গোনা হয় না।

User admin
ব্যবহারকারী ব্যবস্থাপনা

Role অনুযায়ী filter, নাম ও email-এ search, pagination। Role পরিবর্তন করা যায়, তবে নিজের role নয় — যাতে শেষ admin নিজেকে লক করে ফেলতে না পারেন।

Zero-fill
সবসময় সম্পূর্ণ আকৃতি

groupBy শূন্য-সংখ্যক key বাদ দেয়, তাই প্রতিটি status ও role শূন্য দিয়ে পূরণ করা হয় — client-কে অনুপস্থিত key সামলাতে হয় না।

Operations

Config
Boot-এ environment validation

সব variable Zod দিয়ে যাচাই হয়। ভুল থাকলে কোন variable-এ সমস্যা তা ছাপিয়ে process বন্ধ হয় — undefined secret দিয়ে token sign করার সুযোগই থাকে না।

Observability
Request id ও structured log

প্রতিটি request একটি correlation id পায়, যা X-Request-Id header ও প্রতিটি error body-তে থাকে। Log হয় এক লাইনের JSON।

Health
দুই স্তরের health check

/health database ছোঁয় না, তাই uptime monitor বিনা খরচে যত ইচ্ছা ডাকতে পারে। /health/db গভীর check করে এবং অচল হলে 503 দেয়।

Rate limit
Login ও tracking throttling

Redis থাকলে counter সব instance-এ ভাগ হয়, না থাকলে in-memory। Login limiter validation-এর আগেই চলে, যাতে guessing loop-এ body parse করাও খরচ না হয়।

Shutdown
Graceful shutdown

SIGTERM পেলে নতুন connection নেওয়া বন্ধ, চলমান request শেষ, Prisma pool ছাড়া, তারপর exit — ১০ সেকেন্ডের কঠোর সময়সীমা সহ।

Tooling
npm run check

এক কমান্ডে পুরো stack যাচাই: Docker, দুটি container, port, process, database, একটি সত্যিকারের login এবং একটি authenticated read। ব্যর্থ হলে পাশে সমাধানের কমান্ড দেখায়।

০৪ / INTERFACE

ফ্রন্টএন্ড ইন্টারফেস

০৫ / ARCHITECTURE

সিস্টেম আর্কিটেকচার

ছয়টি ডায়াগ্রাম, ছয়টি ভিন্ন প্রশ্নের উত্তর দেয়। প্রথমটি দেখায় কোডটি কীভাবে সাজানো, দ্বিতীয়টি দেখায় একটি request-এর ভিতরে আসলে কী ঘটে, আর বাকিগুলো ডেটা, নিয়ম, অনুমতি ও স্থাপনার ছবি।

০৬ / DATA MODEL

ডেটা মডেল

তিনটি টেবিল, দুটি enum, সাতটি index। primary key হিসেবে UUID v7 ব্যবহার করা হয়েছে, v4 নয় — v7-এর উপরের bit-গুলোতে timestamp থাকে, ফলে তৈরি হওয়া id মোটামুটি সময়ের ক্রমে সাজানো থাকে এবং নতুন row index-এর শেষে বসে, পুরো index জুড়ে ছড়িয়ে পড়ে না।

চালানোর ধাপ

  1. প্রস্তুতি — npm install, তারপর cp .env.example .env। Node ২২ বা তার নতুন সংস্করণ লাগবেই, কারণ অ্যাপটি process.loadEnvFile() ব্যবহার করে।
  2. Secret তৈরি — অন্তত ৩২ অক্ষরের একটি random string তৈরি করে JWT_SECRET-এ বসান। ছোট হলে সার্ভার চালুই হবে না।
  3. Database — npm run db:up দিয়ে Postgres ও Redis container চালু করুন, তারপর npm run db:migrate।
  4. Seed — npm run db:seed — পাঁচজন ব্যবহারকারী এবং সাতটি পার্সেল তৈরি হয়, প্রতিটির সম্পূর্ণ history সহ। আবার চালালেও নিরাপদ।
  5. চালু — npm run dev, এবং npm run check দিয়ে পুরো stack এক নজরে যাচাই করুন।

০১
Rate limiting আরও শক্ত করা

বর্তমানে limiter-এর bucket key প্রথমে cf-connecting-ip header থেকে নেওয়া হয়, আর header পাঠায় client নিজেই। এছাড়া trust proxy ৩-তে সেট, যেখানে এই deployment-এ hop আসলে একটি; এবং store-এ ত্রুটি হলে request পাস করে দেওয়া হয়। তিনটি মিলিয়ে limiter এখন কঠোর নিয়ন্ত্রণ নয়, বরং সাধারণ অপব্যবহারের বিরুদ্ধে একটি speed bump। করণীয়: platform-নির্ধারিত client IP-তে key করা, hop সংখ্যা বাস্তব মানে নামানো, এবং store ব্যর্থ হলে in-memory-তে ফিরে যাওয়া।

০২
Registration হার্ডেন করা

/auth/register-এ কোনো rate limit নেই, এবং নিবন্ধিত ঠিকানার জন্য আলাদা 409 EMAIL_TAKEN ফেরে — অর্থাৎ login যে enumeration সাবধানে বন্ধ করেছে, register সেটি খুলে রাখে। পাসওয়ার্ডের কোনো ন্যূনতম দৈর্ঘ্যও এখন প্রয়োগ হয় না (শুধু bcrypt-এর ৭২ বাইট সর্বোচ্চ সীমা আছে)। করণীয়: limiter যোগ, ন্যূনতম দৈর্ঘ্য নির্ধারণ, এবং নিবন্ধিত ঠিকানার ক্ষেত্রেও একই আকৃতির উত্তর।

০৩
Automated test লেখা

পুরো harness ইতিমধ্যেই তৈরি এবং অব্যবহৃত: createApp() আলাদা করা হয়েছে যাতে test port ছাড়াই অ্যাপ চালাতে পারে, supertest ইনস্টল করা, TEST_DATABASE_URL config-এ যুক্ত, Docker init script আলাদা test database বানায়, এবং rate limiter test পরিবেশে নিজেকে skip করে। যা নেই তা হলো test ফাইল আর একটি npm test script। অগ্রাধিকার: প্রথমে parcelStatus.js-এর transition টেবিল (database লাগে না), তারপর প্রতিটি role-এর scopeFor() দৃশ্যমানতা, তারপর updateStatus-এর 409 race, তারপর register/login-এর enumeration আচরণ।

০৪
assignStaff-এর দুটি race বন্ধ করা

এখানে পার্সেলের status ও লক্ষ্য ব্যবহারকারীর role পড়া হয়, তারপর লেখা হয় — তিনটি আলাদা statement-এ, কোনো transaction ছাড়া। পড়া আর লেখার মাঝে কর্মীকে demote করা হলে পার্সেল non-staff ব্যবহারকারীর নামে থেকে যেতে পারে, অথবা পার্সেল delivered হয়ে গেলে "delivered পার্সেল পুনরায় assign করা যায় না" নিয়মটি এড়িয়ে যায়। করণীয়: updateStatus-এ ব্যবহৃত একই কৌশল — UPDATE-কে পঠিত মানের উপর শর্তসাপেক্ষ করা।

০৫
Error code-এর অসঙ্গতি দূর করা

USER_NOT_FOUND দুটি ভিন্ন status-এ ফেরে — authenticate থেকে 401, আর admin service থেকে 404। যেহেতু client-দের বলা হয়েছে message নয়, code দেখে সিদ্ধান্ত নিতে, একই code-এর দুই অর্থ সত্যিকারের অস্পষ্টতা। করণীয়: হয় আলাদা code, নয়তো একই status।

০৬
ছোট ধারালো কোণাগুলো

GET /parcels/‹uuid› tracking-code route-এ গিয়ে পড়ে এবং 404-এর বদলে 422 দেয়, কারণ id ও tracking code একই path অবস্থান ভাগ করে। trackingLimiter authenticate-এর আগে চলে, তাই একটি unauthenticated request-ও কারও কোটা খরচ করে। Tracking code তৈরির পাঁচটি চেষ্টা শেষ হলে raw P2002 বেরিয়ে 409 DUPLICATE হয়ে যায়, যা client-এর না-পাঠানো একটি মানের জন্য তাকেই দোষ দেয়। আর cors() এখন সব origin-এর জন্য খোলা।
